# Weekly visit calendar

## User's workflow

**Read patient charts only for visits currently scheduled as an initial EVAL.** For every other visit type—including FUV, PTD, REEVAL, PFR, RECERT, and SOC—use the verified agency schedule and existing calendar information only. Do not open patient charts, profiles, assessments, diagnoses, care plans, or referral documents to enrich those entries. A prior calendar event titled EVAL does not authorize chart review when the current visit is another type. If required agency, address, or contact information is missing from the permitted sources, flag the gap for the user rather than opening the chart. Missing clinical background is not a blocker for non-EVAL visits and does not need a placeholder note.

When placing **unconfirmed visits** into timed planning slots, use **45 minutes starting at the top of the hour** (e.g. 10:00–10:45), with no confirmation checkmark. This duration is the user's visual cue for unconfirmed appointments. **Confirmed visits normally use one-hour slots** and the confirmation checkmark described below. Do not treat placement into a timed slot as confirmation. Verify the saved start time and duration, and preserve existing user-arranged slots when they already match this convention. If the user requests recurrence, apply the specified finite number of weeks to the new planning entries; preserve prior-week originals and avoid adding another copy when the requested slot already exists.

Prefix the patient name with the green checkmark **✅** when placing a confirmed visit in its actual time slot, e.g. **✅Surname, Given - FUV**. This indicates appointment confirmation, not visit completion. Sunday all-day staging entries are not marked confirmed just because they were duplicated. Respect the requested confirmation window: for "this week," update only those recurring instances, not the entire series or prior weeks. Do not add duplicate checkmarks.

Supported scheduling sources are **Seniority (UltraHHC), Alta (VTTECS), Light (Kinnser), and In Touch (its new EMR at app.intouchrehab.com or Kinnser)**. In Touch is a staffing company; identify each patient's actual home-health agency from the agency schedule or existing calendar information and include it in the event details separately from staffing. A chart may be used for an initial EVAL only. The user will open the relevant tabs/schedules. Inspect those open tabs when collecting the week; do not overlook Kinnser or the new In Touch EMR. Verify the agency identity shown in each session and collect each requested source's week separately. Do not infer agency identity solely from the domain. If an expected schedule is unavailable or its identity is unclear, report the missing source instead of silently treating the week as complete.

For an individual visit, use the day the user requests rather than the Sunday weekly staging convention. If only a day is given, create an all-day, nonrecurring planning entry on that day with time unconfirmed; do not invent a visit time or confirmation checkmark. For a new In Touch patient scheduled for an initial EVAL, the open patient-specific EMR chart is a valid source for agency, address, contact details, visit type, and clinical background. Other visit types follow the schedule-and-existing-calendar rule above, even for a new patient.

Home-health planning events should have **no Google Meet and no guests**, including the user's own account as an attendee, unless the user specifically requests them. With the Calendar connector, explicitly set `add_google_meet: false`, `attendees: []`, and `self_attendance: "omit"` when creating an event. Verify the saved guest list and conference fields because defaults can add them. Remove inherited guests and conferencing from new duplicates; preserve unrelated original events. If the connector cannot remove existing conferencing, use the browser editor and save without sending guest emails.

In event details, include the actual home-health agency, staffing source when applicable, and useful contact information. **For initial EVAL visits only**, include one short source-grounded sentence about the main diagnosis or reason for hospitalization/SNF care. For other visits, existing useful calendar background may be retained, but do not seek new clinical information or require a diagnosis/history sentence. Do not invent diagnoses or include an EMR/chart link at the bottom.

**Do not add routine scheduling information to event descriptions.** Never append “Weekly planning hold…” or “actual appointment day/time unconfirmed” boilerplate, including when the visit remains an all-day Sunday hold. The calendar fields and title checkmark already show the date, time, recurrence, and confirmation status; do not repeat those details or add generic planning-week, tentative-slot, or unconfirmed-appointment text. Add or retain scheduling notes only when important or different, such as an afternoon-only preference, calling before arrival, or caregiver coordination. Apply this rule when creating copies and moving holds, while preserving useful contacts, access instructions, and other relevant existing information.

Follow this order: read the full agency week and each visit type → reconcile existing calendar entries → look up any missing patient's prior visit → Duplicate the prior visit → update the new title, Sunday/all-day date, and contact notes together → save → verify the copy and unchanged originals. Represent every scheduled visit, including repeated patients, and leave new copies for the user's review. Prefer the Calendar plugin for bounded searches, reading baselines, and batch verification; keep browser **Options → Duplicate** for copying and cleaning notes unless the user requests a different method.

Read each requested Sunday–Saturday week separately from every included agency schedule, prioritizing the week the user specifies. Honor an explicit agency exclusion such as "I'll do Light later" and report it as excluded. Reconcile visits by patient, agency, type, and count against existing timed appointments and Sunday placeholders. Add only visits not already represented; stage each missing visit as a separate all-day entry on that week's Sunday. Two scheduled visits require two represented entries. Do not treat staging as a confirmed appointment time.

In Kinnser, verify the full requested week through **Go To → My Patients → Display Schedule** (staff schedule report). Hotbox can omit future visits, so its absence of tasks does not establish an empty week. Verify the report date range, clinician, Kinnser session agency, and each patient's underlying home-health agency when shown.

Use the existing calendar named **Jason's HH Schedule**, resolving its ID from the connected calendars. The primary calendar may be a different, empty calendar. Use America/Los_Angeles and verify the requested year. Dates vary by request; do not hardcode the example week.

## Preserve prior schedules

The previous week's calendar is used for invoicing. **Never move, edit, clean up, rename, or delete an original visit while planning a new week.**

For the requested current and future weeks, the user authorizes reconciliation to the verified EMR: correct existing visit-type titles, remove visits exceeding the scheduled weekly count, and remove stale entries after discharge or with no visit in the verified full clinician schedule. Check the patient's identity, agency, requested week, and complete schedule before removal; a missing Hotbox item or an old calendar PTD label alone is not enough. A later EMR visit can indicate continued care or a new episode, so retain visits that the current EMR actually schedules. Preserve excluded agencies and ambiguous entries, flagging uncertainty. Prior weeks remain protected for invoicing.

Notify the user **at the end** about every removal, naming the patient, date/time, and reason. Do not ask again for routine corrections covered by this authorization. Target only the relevant recurring occurrences within the requested weeks, never the whole series or past instances. Preserve retained appointment times, notes, location, color, and checkmarks when correcting visit types, unless the user also requests another change.

Before writes, retain a baseline of source event IDs, titles, dates/times, descriptions, locations, and colors. Look up every patient by name first. Search recent prior events, widening the bounded date window for returning patients whose last visit was months ago. Match the full patient identity and agency; do not reuse an unrelated patient's record.

Use Google Calendar's **Options → Duplicate** on the matched prior event. Before editing, verify that the editor is creating a new event (e.g. **Cancel event creation**), not editing the original. Change only the duplicate. Set **Does not repeat** explicitly: duplicating an occurrence can copy its series recurrence and original occurrence date. Then enable **All day**, set both visible start and end dates to the target Sunday, and verify before saving. The stored all-day end date is the following Monday, exclusive.

Wait for **Event saved** before starting another copy. Record the new event ID. Any later connector update must target an ID in the newly-created-copy allowlist or a scoped existing occurrence covered by the user's reconciliation or scheduling authorization. If a save/action times out, inspect state and search for the new event before retrying to avoid extra duplicates. Moving an existing staging copy into a timed slot can show **Event rescheduled** instead of Event saved; verify its resulting date and duration before retrying. If a connector rejects an all-day-to-timed conversion, inspect the unchanged event and use the browser editor for that conversion.

Verify the first copy against the source baseline, then verify in batches and at completion. Check that every source still has its original times, title, notes, location, and color. If anything differs unexpectedly, stop further copying and resolve the discrepancy. On an authorized rollback, compare with the baseline and remove only this attempt's additions; never move a copy back over an intact original. A copied series must be identified and removed as an added series when rolling back.

## Visit types and titles

Read each visit's current type from the agency schedule **before duplicating**, not from the old calendar title. Seniority patient cards show the visit type in their hover popover. Check both the name and date in the tooltip; the previous tooltip can linger briefly after moving between cards. Set the correct title in the duplicate editor along with its date and cleaned description, then save once; do not defer title changes to a separate pass.

Use patient name followed by a hyphen and the current abbreviation: **FUV, EVAL, PTD, REEVAL, PFR, RECERT, SOC**. Seniority PT Visit means FUV; PT Re-Evaluation means REEVAL. **Alta uses Flamingo color and the title abbreviation PFR for reassessments/re-evaluations, not REEVAL.** Alta PT means FUV, PFR stays PFR, and PTD means PTD. Preserve the agency color when duplicating. Do not infer a discharge or reassessment from the prior event alone. Preserve useful title instructions such as a gate code or calling before arrival. Remove inherited status checkmarks and recorded time prefixes from new Sunday staging copies; add ✅ when the new appointment is confirmed and assigned a time slot.

Seniority calendar cards observed at west.ultrahhc.com/Calendar/MainMenuCalendar.aspx use table.mainCalendarPlanned with data-visitid and data-original-title containing status/date. Read the currently displayed DOM to locate cards. Clicking the patient-name or time cell can expose the hover popover without opening Edit. Avoid the agency Edit button, which opens a plan-date editor; cancel it without saving if opened during inspection. Do not change the agency schedule.

## Clean only the new copy

Retain the existing address, contact names/numbers and relationships, gate codes, parking instructions, texting preferences, and useful scheduling preferences. Remove old vitals, subjective visit-day notes, examination findings, dated evaluation/frequency/CLOF/DME text, old appointment-confirmation claims, and routine scheduling boilerplate. Keep important scheduling exceptions and preferences. Do not invent new findings. Preserve pertinent information when its meaning is clear; flag material ambiguities instead of guessing.

When the calendar contact number differs from information already available in the agency schedule or an allowed initial-EVAL chart review, keep the calendar number unless the user directs a contact change. Apply agency-schedule visit types and counts without automatically replacing established calendar contacts. When assigning a staged visit to a requested time, move that existing copy rather than creating another visit.

## New-patient information

For a **new Seniority initial EVAL only**, if no matching prior calendar entry exists after a reasonable name search, use the patient's Seniority referral/update PDF from the user's connected Seniority Gmail account for address and contact information. Verify the Gmail account and patient identity. This email/PDF fallback is authorized for **Seniority initial EVALs only**, not other agencies or visit types. For a genuinely new initial-EVAL patient there is no prior visit to duplicate: create an entry using verified details and the agency's current visit type. For new non-EVAL patients, use the agency schedule and existing calendar information; report missing required details to the user without opening charts or referral PDFs. Never send email or contact patients as part of calendar planning.

For Light, use the verified Kinnser schedule for visit types and preserve the matching prior event's agency color. For In Touch, use its verified new EMR or Kinnser schedule and **Peacock blue (Google Calendar event color ID 7)**, not Blueberry. No special reassessment abbreviation has been specified for Light or In Touch; do not apply Alta's Flamingo/PFR convention automatically. Resolve an unclear visit-type mapping or missing new-patient contact source with the user. The Seniority Gmail/PDF fallback does not extend to Light or In Touch.

## Completion

Verify every scheduled visit is represented at the correct weekly count, counting existing entries. Verify new staging copies are on their target Sunday (or the explicitly requested day for an individual visit) with all-day enabled and no recurrence, correct current visit types, preserved contact/location details, and cleaned descriptions; verify copies moved into timed slots against the requested time and duration. Check the actual home-health agency, brief clinical background for initial EVALs only, agency/staffing color, empty guest list, absent Google Meet, and absence of chart links. Non-EVAL visits do not require clinical-background lookup or a missing-background note. Compare the original-event baseline again, allowing only authorized reconciliation and scheduling changes. Leave the priority week open for review and report additions per week, existing-event changes, every removal, excluded agencies, and unresolved mismatches. Include **unique patient count and total patient visits per week**, excluding personal events; distinguish any retained entries from excluded agencies from the EMR-verified totals. Keep patient-specific data out of this reusable skill.
